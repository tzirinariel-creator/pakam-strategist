# 🚨 נוהל-תקלה — מה עושים כשמשהו נשבר (OPS2)

> נכתב 11.7.2026. מיועד לאריאל (או לכל מי שמתפעל) — צעדים קצרים, בסדר הזה, בלי ניחושים.
> כתובת הפרודקשן: https://pakam-strategist.vercel.app · פרויקט Vercel: `ariel-tzirins-projects/pakam-strategist` · DB: Supabase (פרויקט יחיד = פרודקשן).

---

## 1. האתר לא עולה (שגיאה בדפדפן / מסך לבן / 500)

1. בדקו אם זו הפריסה או הפלטפורמה: פתחו https://www.vercel-status.com — אם יש תקלה ב-Vercel, מחכים; אין מה לתקן אצלנו.
2. `npx vercel ls` בתיקיית הפרויקט — הפריסה העליונה אמורה להיות `● Ready`. אם היא `● Error`:
3. **Rollback מיידי (הצעד החשוב):** בדשבורד Vercel → Deployments → מוצאים את הפריסה הקודמת שהייתה Ready → ⋯ → **Promote to Production**. האתר חוזר לגרסה שעבדה תוך דקה, בלי קוד.
   - מהטרמינל: `npx vercel rollback` (או `npx vercel promote <deployment-url>`).
4. רק אחרי שהאתר חזר — מתקנים את הקוד בנחת, ורק אז פורסים שוב `npx vercel --prod --yes`.

## 2. ה-DB לא מגיב (עמודים נטענים אבל ריקים / שגיאות tRPC בכל מקום)

1. https://status.supabase.com — תקלת פלטפורמה? מחכים.
2. דשבורד Supabase → Project → אם הפרויקט **Paused** (קורה בתוכנית חינם אחרי חוסר-פעילות) → **Restore/Resume**. זו הסיבה הנפוצה ביותר.
3. בדקו את מכסות התוכנית (Database size / bandwidth) — חריגה עוצרת שירות בתוכנית חינם.
4. אם הפרויקט רץ ובכל זאת אין חיבור: Settings → Database → אמתו שה-connection string תואם ל-`DATABASE_URL` שב-Vercel (Environment Variables). שינוי סיסמת-DB בסופאבייס בלי לעדכן את Vercel = בדיוק התסמין הזה.

## 3. עוזר ה-AI (המלך) מת — הצ'אט מחזיר שגיאה

1. הנפוץ ביותר: **גוגל הוציאה את המודל משירות** (ראו gemini-model-must-stay-current). בדקו את `GEMINI_MODEL` ב-Vercel env — אם המודל כבר לא ברשימת המודלים החינמיים הנתמכים ב-https://ai.google.dev/gemini-api/docs/models, החליפו למודל חינמי עדכני ופרסו מחדש.
2. מכסת המפתח המשותף נגמרה → משתמשים עם BYOK ממשיכים לעבוד; המפתח המשותף מתאפס יומית. אין פעולה נדרשת מעבר להודעה למשתמשים אם זה קריטי.
3. שגיאת 401/403 מגוגל → המפתח בוטל; מנפיקים מפתח חדש ב-AI Studio ומעדכנים `GEMINI_API_KEY` ב-Vercel.

## 4. פריסה שברה פרודקשן (האתר עולה אבל פיצ'ר מרכזי נשבר)

1. **קודם rollback** (סעיף 1 צעד 3) — לא מנסים "תיקון מהיר קדימה" כשמשתמשים אמיתיים בפנים.
2. משחזרים את הבאג לוקאלית (`npm run dev`), מתקנים, מריצים את שער-האיכות המלא (`npx tsc --noEmit` + `npx vitest run` + אימות דפדפן), ורק אז פורסים.
3. אם הבעיה במיגרציית-DB: **אין rollback למיגרציות** (התוספות כבר ב-DB). המיגרציות שלנו תוספות-בלבד (additive) בדיוק בשביל זה — קוד ישן ממשיך לעבוד מול סכמה חדשה. מוודאים שזה אכן כך לפני כל מיגרציה.

## 5. גיבויים — סטטוס ⚠️

- Supabase בתוכנית **חינם** מספקת גיבויים יומיים ל-7 ימים אחורה **רק בתוכניות בתשלום (Pro ומעלה)**. בתוכנית חינם — **אין גיבויים אוטומטיים ואין PITR**.
- ⚠️ **שער-בעלים (אריאל):** להיכנס לדשבורד Supabase → Database → Backups ולאמת מה הסטטוס בפועל לפרויקט הזה. אם אין גיבויים — ההחלטה: שדרוג ל-Pro (~$25/חודש, כולל PITR) או גיבוי ידני תקופתי.
- **גיבוי ידני מיידי (עובד גם בחינם):** `npx supabase db dump --db-url "$DATABASE_URL" -f backup-$(date +%F).sql` — כדאי להריץ לפני כל מיגרציה, ולשמור מחוץ לריפו (הקובץ מכיל נתוני משתמשים אמיתיים — לעולם לא לקומיט).

## 6. כללי אצבע

- **תמיד rollback לפני debug** כשמשתמשים אמיתיים נפגעים.
- לא נוגעים ב-DB פרודקשן ידנית; כל תיקון-נתונים עובר דרך קוד שנבדק, או דרך ה-UI.
- אחרי כל תקלה: שורה אחת ב-`docs/משימות-בקרה.md` — מה קרה, מה תוקן, מה נלמד.
